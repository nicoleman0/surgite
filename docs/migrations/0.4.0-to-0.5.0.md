# Upgrading standup-gen 0.4.0 → 0.5.0

0.5.0 is the auth + multi-user release. It adds a `users` table, server-side
sessions, invites, and a non-nullable `owner_id` on every existing table, so
every repo, commit, prompt setting, and shared summary now belongs to a user.

This is a **breaking** upgrade (pre-1.0.0, no deprecation cycle). The API and
the CLI changed; read the whole page before you start.

> **Back up the database first.** This migration alters every table. Use
> `scripts/backup.sh`, or take a plain `pg_dump`. There's a downgrade
> (`alembic downgrade -1`) but a backup is faster and safer if something is off.

## Pick an auth mode

0.5.0 introduces `AUTH_MODE`. It's the single most important choice here.

| Mode | Who resolves a request | Login UI | Use it when |
|---|---|---|---|
| `off` (default) | the bootstrap user, always | none | You're on a trusted network and want exactly the 0.4.0 experience. |
| `single_user` | the bootstrap user, always | none | One operator, but you want the session machinery active (e.g. behind a shared proxy). |
| `multi_user` | a real, logged-in user | `/login` + `/logout` | You're exposing the app to people who aren't you. |

`off` is the default precisely so a 0.4.0 install that pulls 0.5.0 and runs the
migration keeps working unchanged: all data is owned by one bootstrap user and
no login is required.

`multi_user` needs HTTPS for browser sessions. Terminate TLS in front of the
application. For local plain-HTTP testing only,
`DEBUG=true` drops the cookie's `__Host-` prefix and `Secure` flag so a browser
will accept it; never set `DEBUG` in production.

## Upgrade paths

### A. Greenfield

You have no existing data to preserve.

1. Install Docker Compose 2.24.0 or newer and configure HTTPS.
2. Copy `.env.example` to `.env`.
3. Set:
   ```
   AUTH_MODE=multi_user
   BOOTSTRAP_OWNER_EMAIL=you@example.com
   ```
4. Start the current release and bootstrap the administrator:
   ```
   docker compose up -d
   ./scripts/bootstrap-admin.sh
   ```
5. Log in at `/login`, open `/admin`, and create an email-pinned invitation
   for each user. Surgite does not send invitation links; share each link
   privately with its intended recipient.

Current releases do not create or log a first-administrator invitation token.

### B. Existing anonymous deployment

You have a populated 0.4.0 database and want to keep it, owned by you.

1. **Back up** (`scripts/backup.sh`).
2. Pull the current release.
3. Set `AUTH_MODE=multi_user` and `BOOTSTRAP_OWNER_EMAIL=you@example.com` in
   `.env`, then configure HTTPS.
4. Start Compose. Container startup applies the schema migrations:
   ```
   docker compose up -d
   ```
5. Run `./scripts/bootstrap-admin.sh`. It prompts twice for a password and
   claims the passwordless bootstrap owner without changing its user ID or
   repository ownership.
6. Log in at `/login` and confirm the existing repositories and summaries are
   present before inviting colleagues from `/admin`.

What the migration actually does: adds `owner_id` to `repos`, `commits`,
`prompt_settings`, and `shared_summaries` as nullable, backfills every row to
the bootstrap user, then sets the column `NOT NULL`. The bootstrap user is
created from `BOOTSTRAP_OWNER_EMAIL` (lower-cased; `CITEXT` on Postgres) with no
password until `upgrade-from-0.4.sh` sets one.

### C. Hosted-as-multi-tenant

**Not supported in 0.5.0.** There's no way to split an existing single-tenant
0.4.0 database across multiple pre-existing users — the migration assigns
*everything* to one bootstrap owner. Multi-tenant onboarding (orgs, per-tenant
data import) is 0.6.0+.

## Large datasets: pre-create the indexes

The migration creates a plain index on each new `owner_id` column and then runs
`ALTER TABLE ... SET NOT NULL`, both of which take a brief lock. On a small
database (the common self-host case) this is sub-second and you can ignore it.

On a large `commits` table, create the indexes **concurrently before** running
the migration, so the lock window is minimal:

```sql
-- Run against the live 0.4.0 DB before `alembic upgrade head`.
ALTER TABLE commits ADD COLUMN owner_id varchar;
CREATE INDEX CONCURRENTLY ix_commits_owner_id ON commits (owner_id);
-- ...then backfill owner_id yourself and run the migration, which will find
-- the column already present.
```

`CREATE INDEX CONCURRENTLY` cannot run inside a transaction, which is why the
migration itself doesn't use it — it would break Alembic's transactional DDL.

## What changed for the CLI

- `STANDUP_API_TOKEN` is renamed to **`STANDUP_API_KEY`**. The old name still
  works but logs a one-time deprecation warning. Rename it.
- New: `standup --login`, `standup --logout`, `standup --redeem-invite <token>`.
  A successful login stores a session cookie (0600) at
  `$XDG_CONFIG_HOME/standup/session`; `standup --registered <name>` reuses it.
- For unattended/CI use against a `multi_user` instance, set `STANDUP_API_KEY`
  (per-user API keys land in slice 2) instead of logging in interactively.

## Rolling back

`alembic downgrade -1` drops the auth tables and the `owner_id` columns and
restores the old `prompt_settings` unique constraint; your original rows are
left intact. Then redeploy 0.4.0. (Restoring your pre-upgrade backup does the
same thing more bluntly.)
